# Develop buildout

Two things this repo expects from every change, beyond the code itself:
a towncrier news entry, and a linear integration history. Verify the
behavioral side with the `verify-buildout` skill; this skill covers the
process side.

This skill is location-independent: it lives at
`.goose/skills/develop-buildout/` inside the checkout. No
machine-specific path or branch name appears anywhere in this skill —
"base branch" means whatever branch your work is forked from and will
merge back into.

## News entries (towncrier)

`CHANGES.rst` is generated by towncrier — never edit it directly.
Every non-trivial change must carry an entry in `news/`. Full
contributor doc: `doc/ADD-A-NEWS-ITEM.rst`.

- Naming: `<issue-number>.<type>.rst` when an issue exists; otherwise an
  orphan entry `+<8-hex>.<type>.rst` (e.g. `news/+dc7e8ecc.feature.rst`).
- Types (from `[tool.towncrier]` in `pyproject.toml`): `breaking`,
  `feature`, `bugfix`, `develop`, `tests`.
- Content: reStructuredText; all lines are joined into one paragraph, so
  avoid markup that needs multiple lines. Use ```` ``literal`` ```` for
  command and option names. End with the author handle, e.g. `[gotcha]`.
- Validate before committing when towncrier is installed:
  `towncrier --version=X.Y.Z --draft`.
- Classify honestly: new user-visible capability → `feature`; wrong or
  confusing existing behavior made right → `bugfix`.

## Linear history (rebase + fast-forward)

Integration here is rebase-based. Merge commits in a topic stack are a
defect: they tangle review order and break the clean `git log` story.

- Keep topic branches rebased onto the current base branch; never merge
  the base *into* a topic branch.
- Integrating several topic branches: rebase them sequentially onto the
  base (first topic onto base, second topic onto the first, …), producing
  one linear chain. The base branch must end up a direct ancestor of the
  integration head, so the final merge is a fast-forward:
  `git merge-base --is-ancestor base head`.
- No merge commits in the range: `git log --merges base..head` must be
  empty.
- Rewrite only unpublished history. Nothing in this workflow is pushed
  until the owner says so — until then, rebasing and resetting local
  branches is safe. Once a branch is pushed, history is append-only.
- Rebasing preserves authorship; keep the repo-local `user.name` /
  `user.email` identity and match the surrounding commit-message style
  (plain messages, no trailers, unless the repo asks otherwise).

## Rebase and verification evidence

A rebase produces new commits; prior test evidence applies only if the
content is unchanged:

- Compare tree hashes, not commit hashes:
  `git rev-parse HEAD^{tree}` against the previously verified commit.
  Identical trees mean suite results carry over byte-for-byte — do not
  re-run an 8-minute suite on an identical tree.
- If the tree differs (conflict resolution, amended files), rerun the
  verify-buildout ladder before claiming the result verified.
